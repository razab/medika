# Контракт приложения: данные, операции и интерфейс

Правила проекта с 14 ноября 2026. Они обязательны при проектировании и изменении поведения приложения. [USER-FLOWS.md](USER-FLOWS.md) описывает задачи пользователя, [DESIGN-RULES.md](design-study/DESIGN-RULES.md) — размещение данных и действий, этот документ — их технический контракт и Definition of Done. Правка этого документа сама не внедряет схемы и миграции в работающую базу.

## 1. Модель хранения и источник истины

Для Медики выбрана **реляционная модель, основное хранилище — SQLite**. JSON — формат значений и обмена; отдельную NoSQL-модель поверх тех же сущностей не вводим. Объект API, строка таблицы и данные компонента — три представления одной предметной сущности с явным преобразованием между ними.

Фактическая реализация в `site/lib/store.mjs`: таблицы `people`, `medicines`, `prescriptions`, `events` и другие содержат `id` и JSON в `data`; часть ключей вынесена в SQL-столбцы с FK/UNIQUE. Это существующее размещение данных, а не доказательство полной типизации всех полей JSON. `prescriptions.medicineId` внутри JSON, например, не защищён SQL foreign key: существование препарата проверяет сервер.

- У сущности один стабильный ID и один владелец записи. Разные таблицы/объекты не обозначать общим тегом «лекарство»: препарат каталога, назначение человеку и факт приёма имеют разные контракты.
- Для каждого поля указывать точное физическое размещение: БД → таблица → столбец → путь JSON, если он используется. Для связи — целевой тип/ID, кратность, обязательность и поведение при архивировании/удалении.
- Ограничения идентичности, ссылок и уникальности закреплять в БД, где это возможно. Пока связь остаётся в JSON, её обязательную проверку выполнять на сервере в границах соответствующей транзакции; этот предел защиты описывать явно. Дублируемые SQL-ключи и JSON-ID не должны расходиться.
- План, фактическая история и справочник имеют разное назначение. Снимок прошлого факта — осознанная копия с описанными полями, а не второй редактируемый источник истины. Изменение плана не переписывает прошлое.
- Вычисляемые данные имеют формулу, входы и владельца вычисления. Таймер, отображаемый слот, фильтр и раскрытие карточки не становятся сохранённым медицинским состоянием без отдельного требования.
- Хранилище определений атласа `site/data/ui-atlas.sqlite` отделено от клинического `medika.sqlite`. Редактор сценариев не получает полномочий менять лечение. Синтетические JSON-фикстуры не являются рабочей БД.

Эти правила не разрешают автоматически нормализовать/переписывать существующую базу. Изменение физического хранения требует отдельной миграции и проверки сохранности данных.

## 2. Обязательный контракт типа

Для новой или изменяемой сущности/структуры до завершения реализации должны существовать следующие сведения. Для неизменённого типа достаточно ссылки на его актуальный контракт.

| Часть | Что обязательно определить |
|---|---|
| Идентичность | Стабильный ID типа, назначение, границы, версия схемы и источник определения |
| Поля | Имя, точный тип, вложенная структура, enum, обязательность, допустимость `null`, отсутствие поля, пустое значение |
| Значения | Единицы, формат, диапазон, точность, длина/размер коллекции, уникальность и порядок элементов |
| Начальные значения | Конкретный default либо «нет default»; кто и когда его устанавливает; семантика пропущенного поля при create/update |
| Владение | Что вводит пользователь, что приходит из справочника, что создаёт сервер; какие поля доступны для записи/только чтения |
| Связи | Тип и поле ссылки, кратность, проверка существования/принадлежности, удаление/архивирование, отсутствие циклов, если требуется |
| Инварианты | Правила между полями и сущностями, которые нельзя нарушить ни одной операцией |
| Хранение | Точное размещение, индексы/ключи/ограничения, сериализация и обратное чтение |
| Жизненный цикл | Состояния и разрешённые переходы либо явное «отдельного state нет» |
| Потребители | Какие команды/API, проекции, компоненты и UF используют тип/поле |

Политику неизвестных полей определить явно: что отклоняется и что разрешено для совместимости. Поля, доступные только серверу, нельзя менять передачей дополнительного ключа в request. Применение default — явный шаг нормализации в названном месте; одно описание default не означает, что значение присвоится само. Проверять полученное нормализованное значение и сериализованный результат.

Машиночитаемый формат контрактов JSON-значений для проекта — **JSON Schema**; определения request/response и сохраняемых значений должны ссылаться на общие определения типов. Ограничения, которые не выражаются схемой (например, существование связанного человека или допустимость перехода), проверяются отдельными серверными правилами. Схема должна действительно участвовать в проверке данных; наличие файла без вызываемого валидатора не закрывает требование. Внедрение этого формата в существующие ручные валидаторы — ещё не выполненная работа, см. раздел 8.

Не поддерживать независимо три несовпадающих описания типа для формы, API и хранения. Различия DTO и сохраняемой записи разрешены через явно описанный mapping и проверяемые преобразования. Использовать allowlist записываемых полей; не сохранять произвольный объект из формы целиком.

Особые правила значений:

- `null`, отсутствие поля, `""`, `0` и `false` различаются. Для update явно определить, что значит «оставить прежнее», «очистить» и «заменить». Не полагаться на truthy/falsy для дозы, времени и состояния.
- Для числа выбрать один тип и точное представление. Если используется десятичная строка, описать её формат и преобразование; не принимать произвольную смесь number/string. Концентрация упаковки не является разовой дозой.
- Разделять календарную дату, локальные часы с часовым поясом, момент времени и длительность. Неизвестное время не заменять моментом сохранения. Серверное «сейчас» допустимо только для явно определённого действия «принято сейчас».
- Default не является медицинской догадкой. Не достраивать дозу, длительность курса или интервал без источника. Начальное состояние объекта не означает, что пользователь уже совершил действие.
- Версия схемы данных, `record.version` для конкурирующих правок и revision сценария — разные величины. Не добавлять новое поле версии механически: определить место его хранения и миграцию.

## 3. Состояния и переходы

Enum сам по себе не описывает поведение. Для объекта со state обязательна таблица:

| Исходное состояние | Команда и инициатор | Предусловия | Новое состояние | Изменения/побочные эффекты | Отказ |
|---|---|---|---|---|---|
| Точное значение или отсутствие объекта | ID операции/API, роль пользователя/системы | Поля, связанные объекты, версия | Точное значение | Что сохраняется атомарно, аудит, какие данные пересчитываются | Код ошибки и состояние после отказа |

- Перечислить начальное состояние, обратимые и конечные переходы. Неперечисленные переходы запрещены; разрешённые самопереходы, повтор команды и восстановление после отмены описывать явно.
- Проверять переход на сервере. Недоступная кнопка не является защитой состояния. Отклонённая команда не оставляет частичную запись.
- Отдельно описывать сохранённое предметное состояние, вычисленный статус и временное состояние UI (`loading`, `saving`, `error`, черновик). Таймер «истёк» не запрещает запись реально состоявшегося приёма. Отсутствие факта не является сохранённым событием `planned`.
- Исправление/отмена факта сохраняет историю и автора/причину в согласованном объёме. Восстановление записи после отмены — отдельный переход с определённой идентичностью, не неявное создание дубля.
- Если state отсутствует, не придумывать его ради шаблона: зафиксировать разрешённые операции и инварианты объекта.

Пример, подтверждённый текущим `site/server.mjs`: `events.status` при создании допускает `taken`, `skipped`, `deferred`; отдельный `/void` устанавливает `void`. `/correct` разрешает исправление фактического `taken`, но не `void`. Повторный `POST /api/events` после `void` для того же планового ключа обновляет прежнюю запись с аудитом. Полный целевой граф нельзя объявлять внедрённым по этому примеру: все маршруты изменения статуса ещё нужно собрать и сопоставить в едином контракте.

## 4. Контракт операции/API

Каждое действие над данными имеет стабильный ID операции. Для HTTP-операции обязательны:

| Часть | Содержание |
|---|---|
| Вызов | Метод и путь, параметры пути/query/body, инициатор, связанный UF и компонент |
| Вход | Ссылка на тип request, обязательность/nullable/default, источник каждого значения |
| Доступ | Сессия, права и проверка принадлежности объектов; для локального приложения — существующая защита Host/Origin/token |
| Предусловия | Существование, состояние, версия записи/связанных объектов, бизнес-инварианты |
| Изменение | Читаемые/записываемые сущности и поля; точная граница транзакции, аудит, внешние побочные эффекты |
| Ответ | Тип response, HTTP-статус, возвращаемые ID/версии/значения; что подтверждает сохранение |
| Ошибки | HTTP-статус и стабильный код, поле/причина при необходимости, сохранённое состояние и действие восстановления в UI |
| Повтор/конкуренция | Идентичность команды, политика idempotency, устаревшая версия, потерянный ответ, отмена ожидания |
| Обновление UI | Какие query/проекции перечитываются или обновляются из ответа; какие компоненты должны показать результат |

Для чтения дополнительно определить фильтры, сортировку, объём/страницы, форму проекции и поведение пустого результата. У локального действия без API явно указать отсутствие запроса, место хранения его состояния и срок жизни.

Сервер валидирует вход и переход до записи; DTO ответа соответствует контракту и не раскрывает лишние данные. Инварианты защищаются транзакцией, а не несколькими независимыми запросами UI. Ошибка записи или неверный тип не сопровождаются успешным сохранением.

Для команды, которую можно повторить после потери ответа, определить и проверить защиту от дубля. Повтор с тем же ключом и иными данными обязан иметь явный отказ; точный ответ на идентичный повтор фиксируется контрактом. Прерванное ожидание в браузере не доказывает отмену транзакции сервера. UI должен уметь восстановить фактический результат, не отправляя новую дозу вслепую.

Новые HTTP-статусы, error codes и форматы не вводить только в документации: синхронно обновить сервер, потребителей и проверки либо отметить их как целевой контракт, ещё не реализованный.

## 5. Связь со сценариями, тегами и UI

Для каждого изменения должна прослеживаться цепочка в обе стороны:

`UF и его версия → шаг/действие → operation ID → request и правила перехода → сохранённые поля → response/query-проекция → поле компонента → видимый результат UF`

- Тег `data:medicine` должен вести к типу препарата. Тег поля — к конкретному полю этого типа. Тег действия — к операции; экран и компонент — к собственным узлам. Подпись «лекарство» без различения препарата/назначения/факта не закрывает связь.
- Для каждого отображаемого/редактируемого значения указать источник, преобразование/форматирование и возможность записи. «Берётся из базы» и набор имён полей без типов недостаточны. Время таймера, например, должно ссылаться на исходный факт и формулу, а не свободный текст.
- Каждое самостоятельное действие имеет определённый результат: переход, локальное изменение, чтение или запись. Статус объекта не становится кнопкой без соответствующей команды.
- Описать UI для загрузки, пустого результата, редактирования, ожидания записи, успеха, ошибки и конфликта — только применимые состояния. Черновик не теряется при отказе. Оптимистичное отображение, если оно используется, отличимо от подтверждённого результата и имеет восстановление при ошибке.
- Изменение UI может потребовать изменения данных/API; изменение схемы может потребовать миграции и обновления UI. Для правки UF разобрать влияние на все звенья, включая удалённые ссылки, прежние факты и другие потребители. Не подгонять отображение выдуманными полями.
- В атласе хранить ссылки на общие определения, а не вторую независимую схему. Взаимосвязи и типы должны быть доступны по тем же стабильным ID; неизвестные связи и внепилотные части обозначать явно.

Минимальный реальный пример добавления в расписание: `UF07-A → add-from-slot → select-drug → save-rx → POST /api/prescriptions`. `medicineId` указывает на препарат, `personId` — на человека, `dose/unit` — на личную дозу; `routineSlots` и `times` различают привязку к еде и часы. Сервер проверяет выбранный препарат/версию и сохраняет назначение, UI перечитывает семейное представление и показывает новую строку. Это не создаёт `events`. Недостаточно только увидеть открывшуюся форму: нужно проверить запрос, запись и возвращённую строку после перезапуска.

## 6. Проверки и изменение контрактов

- Перед записью проверяются машинные типы/форматы и серверные инварианты. В БД проверяются предусмотренные SQL-ограничения; чтение старой записи и сериализация не должны менять её смысл.
- Для затронутого контракта есть положительные и отрицательные примеры: неверный тип/enum/range, отсутствие обязательного значения, разные `null`/отсутствие/default, недопустимая ссылка/принадлежность и запрещённый переход. Проверять применимые случаи, не размножать тесты неизменённой логики ради количества.
- Для изменения записи проверяются актуальная/устаревшая версия, повтор и потерянный ответ, если операция подвержена им. Отказ должен оставлять состояние и историю в предусмотренном контрактом виде.
- Сквозная проверка использует настоящий UI и API во временной синтетической базе: ввод → запрос → запись → новое чтение → отображение. Затем перезагрузка/перезапуск подтверждают сохранение. Простой `200 OK`, скриншот или список endpoint не доказывают эту цепочку.
- Изменение схемы требует описанной совместимости: чтение существующих записей, преобразование, версия, ошибка/возобновление, backup/restore при затронутом формате. Миграцию сначала проверять на временной синтетической базе с данными прежней версии; не начинать с рабочей семьи.
- Код, схема, операции, UF и атлас обновляются в одной согласованной итерации. Проверка ссылок/fingerprints должна отклонять отсутствующие/устаревшие определения. Пока соответствующего валидатора нет, записать пробел и способ ручной проверки; не выдавать структурную проверку карты за проверку полного контракта.

## 7. Definition of Done

Функция готова в заявленном объёме только при выполнении всех применимых пунктов:

- [ ] Названы UF/версия, вход, итог и существенные ошибки; границы изменения указаны.
- [ ] Задействованные сущности и поля определены типами, ограничениями, default/nullable и источником истины; ссылки разрешаются.
- [ ] Физическое хранение, связи, ограничения, миграция/совместимость определены и соответствуют коду.
- [ ] Состояния и все затронутые переходы заданы; сервер принимает разрешённые и отвергает запрещённые.
- [ ] Request, response, ошибки, доступ, транзакция, конкуренция и повтор операции согласованы с реализацией и потребителями.
- [ ] Каждое поле и действие затронутого UI связано с контрактом; видимый результат соответствует сохранённому состоянию; ошибки дают путь восстановления.
- [ ] Выполнена сквозная проверка сохранения/чтения/отображения, а при сохранённых данных — перезапуска. Миграция/восстановление проверены, если затронуты.
- [ ] Применимые негативные проверки проходят; реальные клинические данные не используются в общих артефактах.
- [ ] UF, схема/контракты, атлас и источники актуальны; отчёт называет проверки и оставшиеся ограничения. Пользовательская правка UF не помечена реализованной раньше кода и проверки.

`N/A` допустимо только с причиной: например, действие меняет локальное раскрытие и не пишет в БД. Неизвестный тип, непрослеженная запись или непроверенный переход в затронутом пути — незавершённая работа, а не `N/A`. Для чистой визуальной правки достаточно сослаться на неизменённые контракты и проверить саму правку; переписывать базу не требуется.

Статус «всё приложение согласовано» требует полного инвентаря сущностей, операций и потребителей. Готовый пилот/один путь не даёт этого статуса всему приложению. Зафиксированные пробелы за пределами изменения остаются отдельными задачами.

|---|---|---|
| Хранение | SQLite, некоторые FK/UNIQUE, транзакции, аудит и версии в `site/lib/store.mjs` | Нет единого полного описания типов всех JSON-полей/связей и их SQL mapping |
| Валидация | Ручные `medicineInput`, `rxInput`, `occurrenceInput` и проверки маршрутов | Единого исполняемого набора JSON Schema request/response/storage пока нет |
| Переходы | Проверки некоторых статусов/версий в обработчиках | Нет полного единого графа состояний и набора проверок всех переходов |
| API | Рабочие HTTP-маршруты в `site/server.mjs` | Нет полного общего контракта операций; текущие ошибки обычно содержат только `error`, не структурированные коды/поля |
| UI Atlas | Карта трёх поверхностей, поля/источники, 10 редактируемых путей, конкретные теги, версии/дифы и задачи | Реестр тегов пока описательный; он ещё не показывает и не валидирует полные схемы типов и контрактов API |
| Проверка карты | `validate_atlas.py` проверяет ссылки, anchors, fingerprints и PNG | Не проверяет значения clinical request/response, SQL-схему или граф предметных переходов |

Следующая техническая итерация по этим правилам — один сквозной типизированный путь, например UF07-A, с исполняемыми схемами, mapping хранения, операцией и отображением контрактов в атласе. Сначала подтвердить этот путь на синтетике, затем расширять. Настоящий документ фиксирует требования; перечисленные пробелы им не объявляются исправленными.
